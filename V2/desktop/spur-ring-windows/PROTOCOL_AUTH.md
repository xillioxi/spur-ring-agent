# Recovered AIZO framing and authentication

This adapter implements the current AIZO/Yanqiang Bluetooth path in Windows Python. It does not load the Android/iOS binaries on Windows. The framing and binding code was recovered from their Java bytecode, inspected with Java 17 `javap -c -p`, and cross-checked against CFR output. The original mobile sources and SDK export bundle were not edited.

## Bluetooth endpoints

`com.eiot.aizo.base.AizoBeConfig` supplies:

| Role | UUID |
| --- | --- |
| Connection GATT service | `0000fe02-0000-1000-8000-00805f9b34fb` |
| Command write | `00000101-0000-1000-8000-00805f9b34fb` |
| Command response notification | `0000010a-0000-1000-8000-00805f9b34fb` |
| Protocol ACK write | `0000010b-0000-1000-8000-00805f9b34fb` |
| Secondary command write | `00000131-0000-1000-8000-00805f9b34fb` |
| Secondary response notification | `0000013a-0000-1000-8000-00805f9b34fb` |

The default advertising filter is a different service: `0000df31-0000-1000-8000-00805f9b34fb`. This comes from server SDK `UuidUtil.genBtDescoveryUuid("")`. It must not replace the FE02 connection service.

`AizoBtCommend$bleDe$2` subscribes to 010A and 013A. `AizoBtCommend$callBack$2$1.connect` creates write helpers for 0101, 010B, and 0131. `writeAck` selects 010B.

The 010B helper is optional: `addGattHelper` returns without creating it when the
characteristic is absent. `writeAck` then returns without sending; this SDK has
no fallback to 0101. Version 0.1.1 mirrors that behavior and requires only the
command/response pair for this integration. The user's physical ring reached
authentication after the original hard requirement was removed.

## Wire format

`com.eiot.aizo.core.BtPackage.tEU(byte[], int, int, int, int, int)` constructs:

```
uint16 BE payload-plus-CRC length
uint16 BE flags
uint16 BE sequence
payload
uint16 BE CRC16-CCITT-FALSE(payload), initial FFFF
```

The flags, most significant bit first, are `sender:2, destination:2, version:4, payloadType:2, ACK-required:1, commandType:2, reserved:3`. Current outgoing commands use sender 2, destination 0, version 3, payload type 1 (hex), ACK-required 0, command type 0, reserved 0: `8340`. ACKs use command type 2: `8350`.

### Negotiated ATT write size (0.1.2 live fix)

The original Android connection requests MTU 247 and configures `BtPackage` with
244-byte writes. Original-JAR vectors now include the complete 68-byte binding
payload: it produces a 76-byte wire frame. The SDK returns four raw pieces at a
20-byte limit and one whole frame at limits 185 or 244. The old desktop code
matched the small-limit encoder but incorrectly forced that limit on a link
which had negotiated MTU 247.

A physical test confirmed the difference: four 20-byte pieces yielded transport
ACK `FF` without a binding reply; one 76-byte ATT write yielded a CRC-valid
`70 70` response, a matching original challenge, successful `70 71 01`, and an
authenticated connection. The ring then answered the `AA 13 01` storage query.
The unmodified production `RingClient` repeated this successfully after the fix;
evidence is `test-output/live-production-v0.1.2.json` in the desktop project.

The Windows writer now reads the characteristic's negotiated no-response write
limit (or MTU minus 3 for response writes), waits briefly if size negotiation is
still settling, and sends a whole command frame. If it cannot fit, it stops with
a clear error before sending a partial handshake. It uses the manufacturer's
100 ms write-serialization delay. The general fragmentation helper remains for
original-JAR parity, but this ring's commands are not arbitrarily sliced in the
Windows transport. Tests model a ring that rejects split ATT command frames,
so round-tripping the same permissive fake parser cannot conceal this defect.

ACK payload values are `00` success, `01` CRC error, `02` request retransmission. ACK sequence echoes the incoming sequence. CRC covers only the payload. The SDK slices the entire encoded frame into contiguous write chunks; individual fragments get no extra headers. Request sequence increments from 0 through `C7C7` inclusive, then wraps to 0 (`BtPackage$maxSn$2` and `BtPackage.tEU()`).

Those values describe ACKs generated by this SDK's local frame-validation code;
they do not establish every firmware's incoming ACK payload meanings. A live
frame from the user's ring used protocol version 1 and one-byte ACK `FF` with a
valid CRC. The original SDK does not interpret that byte as authentication
success or failure. Version 0.1.1 logs it and continues waiting for a validated
`70 70` reply. A type-2 frame containing a full application opcode is dispatched
through normal payload validation, as in the manufacturer decoder.

Incoming sender, destination and four-bit protocol version are metadata in the
original SDK, not admission checks. Version 0.1.1 accepts those fields while
retaining CRC and challenge checks. Outgoing framing stays at the SDK's version
3 default; the received version is used by the manufacturer for OTA behavior,
which is outside this utility's scope.

`PacketCodec` buffers each notification channel independently. Corrupt CRC produces `Packet.crc_valid=False` so the transport can send a CRC-error ACK and must discard that payload. Malformed lengths/unsupported headers raise `ProtocolError`; disconnect or reset the decoder instead of searching arbitrary bytes for a frame boundary. Disconnect also resets any partial packet.

## Original binding exchange

The current server SDK `BtHelper` constructs `AizoBtCommend` with vendor/company ID `A1013D00CN1218HE`. The original app initialization uses name `Dreame Ring` and package metadata `com.aierdream.dreamering`; retain these values when using the existing vendor integration.

The Bluetooth client ID is a separate persistent 32-character identity. The mobile SDK stores it in `LocalSaveInfo.appId`, and `initSdk` accepts an existing 32-character `btConnectId`. A desktop installation must persist its own identity or use an explicitly supplied existing identity. The adapter does not clear ring binding, copy private phone storage, or silently try other identities.

`AizoComHelp.getBindRequest` builds:

```
30 30 01
year%100 month day hour minute second        (six raw calendar bytes)
timezone-quarter-hours language ROM         (one byte each)
Bluetooth-client-ID                         (32 UTF-8/ASCII characters)
;2.1.2;A1013D00CN1218HE;                     (ASCII)
```

The `01` flag is produced by `isNeedEncryption`: this vendor ID ends with `E`. Despite that method name, the inspected binding exchange does not invoke AES. `TimeZoneManager.getTimeZoneIndex` divides the UTC offset by 15 minutes; Hong Kong is 32. `AizoUtil.getLanguage` maps ZH/HK/TW to 0, RU to 2, others to 1. `getRom` maps huawei/xiaomi/oppo/vivo to 1/2/3/4, otherwise 0; Windows uses 0.

`AizoBtCommend$callBack$2$1$connect$3$1` delays 500 ms and submits this command, awaiting a `70 70` payload for up to 60 seconds. `BleResultExtKt.authBean` decodes the reply as:

```
70 70 status UTF8(deviceId;password;deviceType)
```

Status 1 is success. Every other status remains a rejection. The original SDK's error text includes denied binding, another bound device, timeout, and mismatch without a reliable per-status label table. The adapter reports the raw status instead of inventing a reason.

For device types 0 through 3, the original SDK compares the returned uppercase password with `AizoComUtil.encodeTime` of the exact calendar bytes sent in the request. That transform creates six bytes, in this order:

```
(month+163), (day+92), (year%100+30), (second+159), (hour+109), (minute+183)
```

Each result is reduced to one byte and rendered as two uppercase hex characters. A successful comparison sends `70 71 01`; mismatch sends `70 71 00`. The adapter validates before exposing a successful session and rejects malformed success replies. For explicitly returned device types >= 4 the original SDK omits the time-password comparison and the entire `70 71` command; the adapter preserves that source-defined branch.

The original `requestHex(70 71 …)` call is fire-and-forget; no command-specific 7071 response is awaited. The subsequent coroutine resets cached device info, optionally synchronizes watch data, and marks connected. Current server `BtHelper` constructor sets that optional synchronization flag to false. `ServiceSdkCommandV2.notifyBoundDevice` delegates to `DeviceManager.notifyBoundDevice`, which sets local device state, calls success, and calls `getDeviceInfo`; it is not an opaque native/server authorization call.

## Verification and limits

`research/auth/GoldenVectors.java` executes the **original JAR classes**, using the local Kotlin standard library, to generate these cross-language vectors:

| Input | Original SDK output |
| --- | --- |
| Frame payload `8103`, sequence `1234` | `000483401234810305c5` |
| ACK status `00`, sequence `1234` | `00038350123400e1f0` |
| Challenge calendar `[26,11,12,15,44,9]` | `AE6838A87CE3` |
| CRC of ASCII `123456789` | `29b1` |

The original executable output is saved in `research/auth/golden-vectors.txt`. `tests/test_protocol.py` asserts these fixed vectors plus fragmented/coalesced notifications, channel isolation, corruption rejection, sequence wrapping, malformed auth replies, rejection statuses, challenge mismatch, and the type>=4 branch.

These vector checks establish binary parity for framing and the time-password transform. Separately, the production client and packaged Windows 0.1.2 EXE discovered and authenticated with the user's physical AIZO ring, validated its challenge, and retrieved its recording count on 2026-11-12. The ring reported zero recordings. Real recording download/playback, extended session reliability, other binding states, and other firmware versions remain unverified. Other SmartRing/NUS/Speex paths are different protocols.
